# session 接续点模板（resume-point）

> 长会话接近上下文上限、或需要主动关闭时，**关闭前**写这份文件。新 session 启动必读。
> 实战来源：会话跑到 200+ turns 后关闭，不写接续点则下一个 session 丢失全部上下文，重复劳动。3 份接续点跨 session 生效验证。

## 文件位置

```
.claude/coordination/active/resume-point-<task_id>.md
```

闭环后随对应单一起软归档到 `archive/<YYYY-MM-DD>-resume-point-<task_id>.md`。

## 模板

```markdown
# session 接续点 — <task_id>

**前一个 session**：<岗位昵称，如 main-designer / implementer>
**关闭时间**：<YYYY-MM-DD HH:MM>
**本接续点用途**：<一句话：新 session 启动时要恢复什么>

## 已闭环

| 单 | commit | 摘要 |
|---|---|---|
| dispatch-<id> | `<hash>` | <一句话> |
| dispatch-<id> | `<hash>` | <一句话> |

**commit 链**：`<hash1> → <hash2> → <hash3>`

**当前基线**：<测试 PASS/FAIL 数，或其他可量化的项目状态>

## 当前 todo 状态

| 状态 | 单 / task |
|---|---|
| ✅ completed | <单号列表> |
| 🟡 dispatched（待接） | <单号 + 一句话，按接单顺序排> |
| 🟡 pending（待派） | <还没写成单的工作> |

## 关键发现（避免下轮重踩）

- <本轮踩的坑 + 结论>
- <环境 / 工具的非显然行为>

## 待拍板选项

- **<问题>**：选项 α <代价> / 选项 β <代价> —— <倾向 + 理由>

## 下次启动命令

<可直接粘贴的第一条命令>
```

## 必含字段（缺一不可）

| 字段 | 为什么必须 |
|---|---|
| commit 链 | 新 session 对账用；没有它无法确认哪些活已落地 |
| 当前基线 | 判断后续改动有无回归的锚点 |
| todo 状态分类 | 区分「已完成 / 已派待接 / 待派」，避免重复派单 |
| 关键发现 | 踩过的坑不写下来，下个 session 会原样再踩一遍 |
| 待拍板选项 | 悬而未决的决策点，附各选项代价，用户可直接拍 |
| 下次启动命令 | 降低重启摩擦，一行粘贴即续上 |

## 什么时候写

- 会话 turns 数明显偏高、感觉上下文吃紧时
- 主动关闭终端前
- 一批单闭环、准备切换工作线时
- **不要等到被动中断**——断电时来不及写（这正是接续点要解决的问题）

## 与中断恢复的关系

接续点是**主动**的，中断恢复是**被动**的：

- 主动关闭 → 写接续点 → 新 session 读接续点续上
- 被动中断（断电 / 崩溃）→ 没有接续点 → 按 SKILL.md §3.5 中断恢复三分类，靠 `active/` 里单子的 status 字段判定

两者互补。接续点写得勤，被动中断的损失就小。

## 不要做的事

- 不要只写"进行中"这类模糊状态——写具体单号 + status 字段值
- 不要省略 commit hash——hash 是唯一可对账的凭证
- 不要把接续点写成日记——它是**给下一个 session 的操作指令**，不是过程记录
- 不要在接续点里重复设计稿内容——给路径引用即可
