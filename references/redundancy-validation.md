# 真冗余验证（references/redundancy-validation.md）

> v6 可选机制 ⑨。默认关闭，警示多 LLM 17× 错误率。关键任务启用。

## 为什么需要

### 多 LLM 错误率叠加

来源：[towardsdatascience 2024 实证](https://towardsdatascience.com/)：
- 单 LLM agent 错误率：~1%
- 多 LLM agent 串联：~17% 错误率（叠加放大）

### 调研反向案例

- Linux Kernel 2018：单 Linus 失误 → 全社区停下
- XZ Utils 2024：单点疲惫 + 无健康度 → 供应链灾难
- CDPR Crunch：单点决策失误 → 项目崩盘

**解药**：关键任务用 N 个不同身份并行执行 + 投票共识。

## 何时启用

满足任一即启用：
- 关键路径（不可逆 / 难回滚）
- 高价值（涉及金钱 / 安全 / 用户数据）
- 单点历史上有过失误
- main 主动决定

## 实施模式

### 模式 A：双 agent 对照

```
- 招两个不同身份的 subagent 跑同一任务
- 比对结论：
  - 一致 → 取该结论
  - 不一致 → main 决定（不重跑，看两份结论差异）
```

### 模式 B：多 agent 投票

```
- 招 N 个不同身份的 subagent（建议 N=3 或 N=5）
- 收集 N 份结论
- 投票：
  - 多数决 → main 采纳
  - 不一致 → main 召集讨论
```

### 模式 C：交叉验证

```
- Agent A 用方法 X 验证 Agent B 用方法 Y 验证的结论
- 双重检查后才采纳
```

## 模板

启用时 main 在派发材料加：

```
真冗余模式：模式 A / 模式 B / 模式 C
N 个不同身份：<身份列表>
投票规则：多数决 / 全员一致 / main 最终决定
```

## 资源开销

- 模式 A：2x token + 时间
- 模式 B：Nx token + 时间（建议 N=3）
- 模式 C：~1.5x token + 时间

**权衡**：只在关键任务启用，避免资源爆炸。

## 与 v6 原则的关系

- 原则 7（可信度写死）：真冗余模式下，每份结论都要走 §四 四条
- 原则 8（健康度挂钩）：真冗余模式可作为告警响应方式之一
- 原则 5（规模自适应）：N 不要太大（建议 ≤ 5），否则又踩 n(n-1)/2 复杂度

## 与已有方案的关系

- 借鉴：Brooks 外科手术团队（精干强主 + 双主治）
- 借鉴：金融系统"四眼眼"原则（dual control）
- 借鉴：Kubernetes Pod 中多容器协同

## 不要做的事

- 不要把所有任务都开真冗余——资源开销爆炸
- 不要让 N 个 agent 共享同一上下文——错误传播
- 不要让投票结果不可追溯——必须留痕
- 不要让真冗余替代可信度条款——是补充不是替代
