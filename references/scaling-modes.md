# 规模自适应 / 小项目旁路模式（references/scaling-modes.md）

> ⚠ **未经实战验证**（截至 2026-09-08）。本文件描述的机制在唯一试用项目里从未触发——该项目规模为 1 人 + 2 终端 + 3 身份卡，按 SKILL.md §0 原则 5 直接落进小项目旁路模式。小项目可跳过本文件。

> v6 原则 5。默认 ≤ 6 卡硬上限；模块数 ≤ 3 自动进旁路模式。

## 规模档位判定

| 档位 | 模块数 | 贡献者数 | 代码量 | 协议复杂度 |
|---|---|---|---|---|
| 小作坊 | ≤ 3 | ≤ 2 | < 10K 行 | 低 |
| 中型 | 4-10 | 3-8 | 10K-100K | 中 |
| 大型 | 11-15 | 9-15 | 100K-1M | 高 |
| 超大 | > 15 | > 8 | > 1M | 极高 |

注：任意一项超阈值即跳到更高档位。

## 各档位的配置

### 小作坊（≤ 3 模块 + ≤ 2 贡献者）

**简化配置**：
- 只发 id-card-main-designer.md
- 占位登记表 / 任务清单 / 协议走简化模板（可省略）
- 跳过可信度写死（main 自己验）
- 跳过健康度挂钩（CHAOSS 对小项目不适用）
- 健康度仪表盘可延后到中型规模启用

**反例警示**：Stardew Valley / Celeste / 早期初创——1-2 人项目强行派卡 = 50% 沟通开销 + 30% 速度损失

### 中型

**完整配置**：
- 走完整 8 原则
- 身份卡可招 ≤ 4 个
- 健康度挂钩启用（轻量）
- 重议周期可放宽到 8 周

### 大型

**强化配置**：
- 身份卡 ≤ 6 硬上限（默认满档）
- 健康度挂钩强制启用
- 重议周期 4 周强制
- 强制独立验证岗

### 超大

**警告 + 分权建议**：
- 强制触发分权警告（co-main / 委员会）
- 重新评估 Conway 是否还成立（可能需要拆分项目）
- 健康度挂钩必须实时
- 重议周期可缩到 2 周

## 突破 ≤ 6 硬上限

### main 主动调整

```
1. main 在 PR 描述里写明理由：
   "本项目需要 N 张卡，因为：<具体业务原因>"
2. 至少 1 个 reviewer approve（co-main 或可信岗）
3. 突破后必须在登记表加备注
```

### 用户特殊需求

用户在调用 skill 时说：
- "此项目需要 8 张卡，因为：<原因>"
- "这是大型分布式系统，5 个微服务 × 2 个岗 = 10"

main 听到这种明示即不硬上限，但仍在登记表加备注。

### 留痕要求

所有突破必须写明：
- 突破者（main / 用户）
- 理由（具体到业务需求）
- 风险评估（co-main 是否就绪 / 健康度阈值是否调整）

## 反向案例

| 案例 | 教训 | v6 对应机制 |
|---|---|---|
| Stardew Valley | 1 人项目不需要协议 | 小作坊旁路 |
| Linux 2018（Linus 休假） | 单点疲惫 | main 负载上限 |
| XZ Utils 2024 | 单点疲惫 + 无健康度 | 健康度挂钩 |
| Valve 隐性等级 | 无结构催生隐性 | 默认 main + 显式岗 |
| RACI 膨胀 | 派卡无上限 | ≤ 6 硬上限 |

## 反 Conway 检查

大型项目必须做反 Conway 检查：
- 当前代码架构是否反映组织沟通结构？
- 若不反映，可能需要 Inverse Conway（先画架构再倒推组织）

参考 references/conway-inverse-maneuver.md
